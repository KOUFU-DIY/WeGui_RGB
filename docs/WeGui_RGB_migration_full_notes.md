# WeGui_RGB 显示架构分析与移植改造说明

> 仓库：`KOUFU-DIY/WeGui_RGB`
>
> 目的：整理当前工程显示机制、缓存结构、CPU 开销来源，以及后续面向 `全屏缓存 + 双行缓存 + DMA + 脏区重绘` 的移植方向，便于后续在新工程中复用，并作为给 AI 的背景说明文档。

---

## 1. 工程当前显示机制总结

WeGui_RGB 的 GUI 逻辑和菜单动画层是比较完整的，但它的显示缓存与输出机制，本质上是从 **单色 OLED 页写入(page addressing)** 和 **常规点阵字体/图标取模方式** 演化而来，再扩展到低位深多色和 RGB565 TFT 输出。

### 1.1 核心缓存结构

工程当前使用的显存结构为：

```c
uint8_t LCD_GRAM[GRAM_YPAGE_NUM][SCREEN_WIDTH][LCD_COLOUR_BIT];
```

这个结构的含义不是“逐像素 framebuffer”，而是：

- 第 1 维：`GRAM_YPAGE_NUM`
  - 屏幕按 **8 像素高** 切页(page)
  - 例如 240 高屏幕，共 `240 / 8 = 30` 页
- 第 2 维：`SCREEN_WIDTH`
  - 横向列 x
- 第 3 维：`LCD_COLOUR_BIT`
  - 颜色位平面(bitplane)数量
  - 1bit -> 2 色
  - 2bit -> 4 色
  - 3bit -> 8 色

即：

- `LCD_GRAM[page][x][k]` 表示：
  - 在第 `page` 页
  - 第 `x` 列
  - 第 `k` 个颜色位平面
  - 对应纵向 8 个像素点的数据

### 1.2 这种结构的来源

它和以下两类传统结构高度一致：

1. **单色 OLED 的 page 写入模式**
   - SSD1306 / SH1106 / SH1107 / SH1108 等常见控制器使用 page addressing
   - 一页高 8 像素
   - 一个字节表示纵向 8 个点

2. **常规字体/图标取模数据格式**
   - 点阵字库、图标 bitmap 很多都使用“纵向 8 位对齐”的存储格式
   - 工程中的 `gram_draw_one_byte()` 就是围绕这种点阵格式设计的

因此，这个工程本质上是：

> 先按单色点阵 page 结构组织图形数据，再通过多个 bitplane 叠加出低位深颜色，最后映射输出到 RGB565 屏。

## 2. 当前工程的四种缓存/刷新模式

工程当前支持四种模式：

1. `_FULL_BUFF_FULL_UPDATE`
   - 全屏缓存 + 全屏刷新
2. `_FULL_BUFF_DYNA_UPDATE`
   - 全屏缓存 + 动态刷新（CRC）
3. `_PAGE_BUFF_FULL_UPDATE`
   - 页缓存 + 全屏逐页刷新
4. `_PAGE_BUFF_DYNA_UPDATE`
   - 页缓存 + 动态刷新（CRC）

### 2.1 页缓存模式的工作方式

页缓存模式下：

- `LCD_GRAM` 不是整屏，而只是当前若干页的缓存窗口
- `lcd_refresh_ypage` 表示当前缓存窗口对应屏幕上的哪一页
- 每次绘图函数只会把“当前页窗口相交部分”写入缓存
- `LCD_Refresh()` 把这几页发出去后，窗口下移，继续下一块

这就是为什么：

- 一个大矩形不会一次性完整进入缓存
- 一个按钮里的汉字/边框/背景会被拆成多轮页写入
- 菜单动画本质是“参数变化 + 每页反复重绘”

### 2.2 全屏缓存模式的工作方式

全屏缓存模式下：

- `LCD_GRAM` 始终保存整个屏幕的完整低位深画面结果
- 所有控件都直接画到这块完整缓存上
- 刷新时再把整屏缓存或变化区域发到 TFT

全屏缓存模式相比页缓存：

- 少了大量“按页重复重绘”的开销
- 更适合 MCU 还要同时处理其他任务的场景
- 但会占用更多 RAM

---

## 3. 当前结构的优点与缺点

### 3.1 优点

#### 3.1.1 极省 RAM

例如 320x240，3bit 模式：

- 真彩 RGB565 framebuffer：`320 * 240 * 2 = 153600B`
- 当前结构：`(240/8) * 320 * 3 = 28800B`

内存占用大幅下降。

#### 3.1.2 适合点阵绘图

对以下内容非常友好：

- ASCII 字体
- UTF8 / 汉字点阵字库
- 图标
- 单色或低色深 bitmap
- 简单几何图形

#### 3.1.3 与单色 OLED 结构天然兼容

缓存组织方式和很多 OLED 控制器访问模型一致，因此易于兼容单色屏和低资源场景。

#### 3.1.4 便于做低位深多色 GUI

通过 bitplane 可以扩展成：

- 1bit = 2 色
- 2bit = 4 色
- 3bit = 8 色

输出时再通过调色板映射到 RGB565。

---

### 3.2 缺点

#### 3.2.1 不是逐像素直观 framebuffer

访问一个像素 `(x, y)` 时，必须先计算：

- `page = y / 8`
- `bit  = y % 8`

再去对应 bitplane 中取 bit。

#### 3.2.2 输出到 TFT 时需要额外展开

TFT 需要的是逐像素 RGB565 流，而当前缓存是：

- page 化
- bitplane 化
- 低位深颜色索引化

所以每次输出都要做低位深 -> RGB565 的展开。

#### 3.2.3 页缓存模式 CPU 开销高

页缓存模式下，为了省 RAM：

- 每一页刷新前都要重新绘制当前页相交的所有控件局部
- 动画和复杂 GUI 会导致大量重复计算

这也是当前工程 CPU 占用偏高的主要原因之一。

#### 3.2.4 不适合复杂真彩 GUI

例如以下效果并不适合：

- alpha 混合
- 半透明
- 任意颜色渐变
- 真彩图层叠加
- 高色深动画

## 4. 现有 GUI 逻辑层的价值判断

当前工程最值得保留的部分是：

- 菜单结构体与菜单树逻辑
- 多级菜单切换机制
- 动画推进逻辑（如 `Value_Change_PID_P(...)`）
- 控件组织方式（按钮、message、slider、checkbox 等）
- UTF8 / 汉字字体绘制接口
- 统一绘图接口（`lcd_fill_box`、`lcd_draw_utf8_string`、`lcd_draw_bitmap` 等）

也就是说：

> 当前工程最值得保留的是“GUI 逻辑层和绘图接口层”，
> 而最需要重构的是“显示后端与刷新链路”。

### 5.1 总体目标

## 6. 推荐的新显示后端架构

推荐采用：

> **低位深全屏缓存 + 双行 RGB565 缓存 + DMA 行发送 + 脏区重绘**

### 6.1 设计目标

在不推翻现有 GUI 绘图体系的前提下，实现：

- 降低页缓存反复重绘造成的 CPU 开销
- 降低 TFT 输出时 CPU 对总线时序的参与度
- 让 MCU 有更多余量去处理其他任务

### 6.2 建议结构

#### 6.2.1 低位深全屏缓存（保留）

继续使用：

```c
uint8_t LCD_GRAM[GRAM_YPAGE_NUM][SCREEN_WIDTH][LCD_COLOUR_BIT];
```

但只工作在“全屏缓存”思路下，不再使用页缓存滚动窗口。

#### 6.2.2 双行 RGB565 缓冲

新增：

```c
uint16_t lcd_linebuf[2][SCREEN_WIDTH];
```

用于：

- 从低位深全屏缓存中逐行展开 RGB565
- DMA 连续发送一整行到 TFT

#### 6.2.3 脏区管理

新增 dirty rect 管理模块，用于：

- 绘图时标记哪些区域发生变化
- 刷新时只处理变化区域

#### 6.2.4 DMA 行发送

底层 TFT 输出不再逐像素阻塞发送，而是：

- 逐行展开到 line buffer
- DMA 一次发送一整行或一段连续像素

---

## 7. 建议的新刷新流程

新的工作流程建议如下：

```text
GUI逻辑更新
    ↓
控件调用 draw_xxx()
    ↓
draw_xxx() 写低位深全屏缓存 + 标记 dirty
    ↓
主循环发现需要刷新
    ↓
获取 dirty 区域
    ↓
对 dirty 区域逐行展开成 RGB565 到双行缓存
    ↓
DMA 一行一行送到 TFT
    ↓
清除 dirty
```

---

## 8. 行展开逻辑说明

当前缓存按 page + bitplane 存储，因此当需要展开屏幕第 `y` 行时：

- `page = y >> 3`
- `bit  = y & 0x07`

对于每个像素 `x`：

```c
b0 = (LCD_GRAM[page][x][0] >> bit) & 1;
b1 = (LCD_GRAM[page][x][1] >> bit) & 1;
b2 = (LCD_GRAM[page][x][2] >> bit) & 1;
idx = b0 | (b1 << 1) | (b2 << 2);
rgb565 = lcd_driver.colour[idx];
```

然后写入：

```c
linebuf[x] = rgb565;
```

如果只刷新脏区 `[x0..x1]`，则只展开该范围。

---

## 9. 脏区重绘建议

### 9.1 最简单起步方案

先做一个 **全局 union 脏区**：

- 每次绘图扩大脏区范围
- 刷新时按该大矩形逐行刷新

优点：

- 实现简单
- 调试方便

缺点：

- 多个小变化区域可能合并成较大区域

### 9.2 后续优化方案

后续可以升级为：

- 多脏区数组
- 相交或相邻脏区自动合并
- 脏区数量超限时退化为整屏刷新

### 9.3 动画场景注意事项

对于会移动的控件（如光标、滚动条、tip、弹窗），脏区不能只记录新位置，还要记录旧位置：

```text
dirty = union(old_rect, new_rect)
```

否则会出现残影。

---

## 10. 为什么推荐这套方案

对于拥有 128KB RAM 的 MCU，这套方案的平衡性很好：

### 10.1 内存可接受

以 320x240、3bit 全屏缓存为例：

- 低位深全屏缓存：28800B
- 双行 RGB565 缓冲：1280B
- 合计约 30KB 左右

远低于 128KB RAM 上限。

### 10.2 CPU 压力显著低于页缓存反复重绘

因为：

- 全屏缓存始终保存完整 GUI 结果
- 刷新时不需要每页重新组织和重绘大量图元
- 只做逐行展开和 DMA 发送

### 10.3 适合 MCU 还要处理其他任务

显示过程可拆成：

- CPU：做 GUI 状态推进、行展开
- DMA：负责 TFT 数据传输

这样 CPU 可以从原先的逐像素发送参与中解放出来。

---

## 11. 推荐的迁移步骤

### 第一步：改为“低位深全屏缓存 + 阻塞行刷新”

先不要急着直接做 DMA 和复杂脏区，先把架构跑通：

- 全屏缓存写入
- dirty union
- 逐行展开 RGB565
- 阻塞发送到 TFT

目的是先验证显示逻辑正确。

### 第二步：加入 DMA 行发送

将阻塞行发送改为 DMA。

### 第三步：加入双行缓冲

实现：

- DMA 发送当前行
- CPU 同时准备下一行

形成流水线。

### 第四步：从单脏区升级到多脏区

减少无谓刷新。

## 13. 一句话总总结

WeGui_RGB 当前的显示结构，本质上是一个从 **单色 OLED 页缓存 + 点阵字模绘制** 演化出来的 **低位深多色 GUI 框架**；其优势是极度省 RAM，劣势是输出到 RGB565 TFT 时 CPU 展开和页重绘成本较高。对于拥有更大 RAM 且 MCU 需要处理其他工作的场景，最合理的移植方向是：

> **保留现有 GUI 逻辑层与低位深全屏缓存结构，重构显示后端为：全屏缓存 + 双行 RGB565 缓存 + DMA 行发送 + 脏区重绘。**

---

### 14.1 背景说明

当前项目参考 `KOUFU-DIY/WeGui_RGB` 的 GUI 逻辑层，保留其：

- 菜单树结构
- 动画推进逻辑
- 控件组织方式
- UTF8 / 汉字点阵绘制接口
- 低位深逻辑显存结构

当前显存组织方式为：

```c
uint8_t LCD_GRAM[GRAM_YPAGE_NUM][SCREEN_WIDTH][LCD_COLOUR_BIT];
```

其中：

- `GRAM_YPAGE_NUM = SCREEN_HIGH / 8`
- `SCREEN_WIDTH` 为屏幕宽度
- `LCD_COLOUR_BIT` 为颜色位平面数量（通常 1/2/3）

### 14.2 当前问题

原始工程的页缓存/刷新方式 CPU 占用较高，原因包括：

- 页缓存模式下，每页刷新前都要重新绘制当前页相交的所有控件局部
- 输出到 RGB565 TFT 时，需要从低位深 bitplane 结构展开成 RGB565

---

### 14.3 改造目标

请保留原有 GUI 逻辑层与绘图接口层，重构显示后端，实现：

1. **全屏缓存**
   - 保留 `LCD_GRAM[page][x][bitplane]` 作为低位深逻辑全屏缓存
   - 不再使用页缓存滚动窗口模式
   - 不再依赖 `lcd_refresh_ypage` 做页级绘制窗口判断

2. **脏区重绘**
   - 所有绘图操作在写入全屏缓存时，同时标记脏区
   - 刷新时只刷新脏区，不做整屏无脑刷新
   - 对于动画对象（光标、滚动条、弹窗、tip等），必须同时记录旧区域和新区域，防止残影

3. **双行 RGB565 缓存**
   - 新增两个 line buffer：
     ```c
     uint16_t lcd_linebuf[2][SCREEN_WIDTH];
     ```
   - 刷新时将低位深全屏缓存逐行展开成 RGB565 写入 line buffer

4. **DMA 行发送**
   - 通过 DMA 将每一行或每个脏区行段发送到 TFT
   - 尽量让 CPU 与 DMA 并行工作
   - 不允许逐像素阻塞写 TFT

### 14.8 绘图函数改造要求

所有绘图函数应修改为：

1. 只做整屏边界裁剪
2. 直接写低位深全屏缓存
3. 同时标记脏区

不要再保留“当前页窗口是否相交”的裁剪逻辑。

例如：

- `lcd_fill_box(...)` 写完整屏缓存后调用 `lcd_mark_dirty(...)`
- `lcd_draw_utf8_string(...)` 根据字符串包围盒标记 dirty
- `lcd_draw_bitmap(...)` 根据图像范围标记 dirty

### 14.9 动画与脏区处理要求

对所有会移动或尺寸变化的对象，必须处理：

- 旧区域 dirty
- 新区域 dirty

典型对象包括：

- 菜单光标框
- 滚动条
- 弹窗
- 提示框
- 动态数值区域

如果只标记新区域而不标记旧区域，会导致残影。

加入双行缓存，让 CPU 展开和 DMA 发送形成流水。

#### 第四步
将单一 dirty 区升级为多 dirty rect + 合并策略。

### 14.11 验收标准

重构完成后，至少应满足：

1. 保持原菜单逻辑和动画视觉效果基本一致
2. 在无界面变化时，不应持续整屏刷新
3. 在局部控件变化时，只刷新变化区域
4. TFT 输出应通过 DMA 按行/按区域块发送，而不是逐像素阻塞发送
5. 代码结构清晰分层，GUI 逻辑层不应直接耦合 DMA 细节
6. 所有动画对象都不应出现旧位置残影
